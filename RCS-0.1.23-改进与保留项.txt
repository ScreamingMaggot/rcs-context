RCS 0.1.23 改进与保留项
================================================================================
插件版本：CONTEXTinjector v1.10.29（LOGcompiler 同步修复）
上一版基线：v1.10.27（DSH session-format v4 兼容）
本包含并：0.1.22 的全部改动（其说明随包分发）
回退点：rcs-0.1.23 → rcs-0.1.22 → rcs-0.1.21 → … → rcs-0.1.8

本版主题：**修复 DSH 0.1.7 的第十一处漂移——工具痕迹从压缩上下文里整类消失**


--------------------------------------------------------------------------------
一、症状与发现路径
--------------------------------------------------------------------------------
2026-09-29 一次真实长任务（会话 5fe3512e，12 回合内 107 步 / 118 次工具调用）首次触发折叠后，
用户核对只增日志发现：118 条工具行全部是

    [T] ?|?|-|OK|P1

即"工具名 | 目标"两列皆空。追查中把**实际注入给模型**的两个转录节点取出来核对，发现比日志
更严重的情况：

    seq=702  replace 10..41     9,892 B /  20 行   [ROUND]1 ×1  [U] ×1  [S] ×1  [C] ×1  [R] ×14  [A] ×2
    seq=703  replace 44..698   10,887 B /  67 行   [A] ×65  [U] ×1  <无标记> ×1
    ─────────────────────────────────────────────────────────
    合计 87 行，其中 [T] 行数 = 0

被折叠的是 205 个节点、465,068 字节；换上的 87 行里**一条工具记录都没有**。也就是说模型
接下来每一轮看到的"历史"只剩"我说过 65 句话"，完全不知道 read/edit/write/pwsh 动了什么。


--------------------------------------------------------------------------------
二、根因：0.1.7 改的是"工具结果放在哪"，不是"叫什么"
--------------------------------------------------------------------------------
0.1.5 及更早，工具结果消息的 content 内含

    {type:'tool-result', toolCallId, isError, content:[…]}

0.1.7 起，同一条结果变成

    {role:'tool', toolCallId:'call_00_…', isError:false,
     source:{kind:'tool', callId:'call_00_…'},
     content:[{type:'text', text:'…'}]}          ← 没有 tool-result 块，id 与 isError 上移到消息层

两处代码都只认块级形态，于是：

1) contextinjector.transcribeIncremental —— 产 [T] 的分支是 `if (b.type === 'tool-result')`。
   该分支永不进入 ⇒ 整条结果消息被静默跳过 ⇒ **折叠丢内容**。
2) logcompiler 的 'tool/result' 事件处理 —— `callId = resultBlocks[0]?.toolCallId`。
   resultBlocks 恒空 ⇒ callId=undefined ⇒ pendingCalls 查不到 ⇒ 兜底 `{op:'?',path:'?'}`
   ⇒ 表现为日志里的 `?|?`（比 1) 轻，因为它至少还产出行）。

工具名本身一直都在：`tool/call` 事件的 data 里有 name 与 arguments（实测 118/118 可得，
分布 pwsh 46 / edit 32 / write 16 / web_fetch 7 / read 5 / web_search 4 / job_output 4 /
todo_write 2 / grep 1 / read_image 1）。是插件没去对的层取。


--------------------------------------------------------------------------------
三、本版做了什么
--------------------------------------------------------------------------------
A. 转录改**双形态**识别（contextinjector.mjs）
   新增 isToolResultMsg(m) / toolResultCallId(m, block)：消息 role==='tool' 或
   source.kind==='tool' 也算结果，callId 依次取 块 → 消息 → source，isError 缺失时回落消息层。
   块级与消息级共用同一个 emitToolRow，保证输出逐字同形；老宿主走原分支，行为不变。

B. 新增**覆盖守卫**（本版真正想留下的东西）
   折叠提交前比对：增量里每个工具结果消息都必须产出一行 [T]，
   got < want ⇒ 拒绝本次折叠、本轮按原文发送，并打印 fold-rejected-coverage。
   动机：旧的五项提交前校验比的是字节与关键值，对"少产出行"完全不敏感——本次事故里
   它照样判定通过并提交了 465 KB→20 KB 的折叠。**宁可这一轮不省，也不带着"看起来完整、
   其实缺整段"的历史继续**，这条纪律现在有了机器执行。

C. LOGcompiler 同步回落消息层（修掉 `?|?`）。

D. 事件层索引 callIndexFromEvents 作为兜底保留：万一某代宿主连派生的 tool-call 块也不给，
   仍可从 tool/call 事件恢复工具名与目标。

E. 回归测试 tests/drift11-toolcall-event-index.test.mjs（18 条断言）。
   ⚠ 测试先把交付文件装配成**安装布局**（profiles/web + profiles/condense + profiles/toolfold）
   再 import —— 仓库是平铺的，直接 import 会解析到仓库外；顺带验证交付包结构本身可加载。
   断言含：0.1.7 消息级形态产出 [T] 且带名字与目标、isError 生效、覆盖 parity、
   双形态判定不误认普通消息、老宿主行为逐字不变。

--------------------------------------------------------------------------------
五、重要更正：v1.10.27 的"v4 兼容性已全验"不成立
--------------------------------------------------------------------------------
0.1.22 交付说明里写的"v1.10.27 适配 + 折叠 v4 全验（23 次折叠 / 0 错误 / 前缀单调）"，
**校验维度不足，结论作废**。当时验的是：折叠次数、字节单调、前缀不回写、错误计数为零——
这些在丢内容的情况下**同样全部成立**（本次事故就是 465 KB→20 KB 且零报错）。
缺的正是本版补上的那条：**被遮蔽节点与产出行的覆盖比对**。

教训记法：验证"压缩没出错"不能只看压缩器自己的账，必须看**压缩后还剩什么**。


--------------------------------------------------------------------------------
六、保留项与已知边界
--------------------------------------------------------------------------------
1. 覆盖守卫目前只盯 [T]（本版事故类别）。[A]/[U]/[R] 的覆盖仍靠字节比对。
   泛化到"每个被遮蔽的非系统节点都须有行"是下一步，但需先确认哪些节点类型允许零行
   （空正文、纯 reasoning 块），否则会造成误拒——按"无读数不改行为"的规矩，本版不预先加。
2. 事故会话（5fe3512e）已提交的 87 行转录不回写：单调前缀纪律不许改已提交内容。
   其补救走"截断日志到折叠之前 + 重启宿主"，见交付说明外的操作记录。
3. 本报告不含用户任务正文；样例命令文本为该测试环境自有内容。
