二、0.1.19 新增：DSH compaction 让路（真机事故复盘）
--------------------------------------------------------------------------------
### 事故
会话 `session-0cea2d8f-bd74-4a4d-b8cd-8c44c39f8792`（单压缩档、长期运行）在 2026-09-12 22:09 彻底无法继续：
```
turn/end      error: This model's maximum context length is 1048576 tokens.
                      However, you requested 1086224 tokens (830224 in the messages, 256000 in the completion)
compaction/end error: compaction: session surface changed during summarization
turn/end      error: 同样超限（重试）
compaction/end error: 同样报错     ← 死循环
```
### 复盘：三个原因叠加
1. **转录无界增长（结构性，尚未修，见 §四）**：该会话 21 次折叠里，转录字节 **6,711 B → 409,972 B**
   （53 → 3,311 行），近期每折 `shrink` 0.85~1.00（最后一折正好 1.000）。
   折叠是"把浓缩后的增量**追加**到累积转录上"，**老内容从不重压** ⇒ 转录逐渐变成整段对话的第二份副本，
   最终把请求顶到 830K token。
2. **我们打断了 DSH 的救命 compaction（致命，本版已修）**：DSH 的 compaction 先 snapshot surface、
   让模型总结、结束时校验"surface 未变"；我们的折叠恰在此时提交 `surfaceOp replace`
   ⇒ 它的总结**作废**（不可逆），而我们的折叠只是延后（可重做）——取舍反了。
3. **DSH compaction 自己也可能写不完（DSH 侧配置）**：`dsh-compaction-basic` 的总结输出上限默认
   **8,192** token（`lib/index.js` L70 `maxTokens: config.maxTokens ?? 8192`），对 ~800K token 的 region
   必然写到一半被截断 ⇒ `summarization truncated at the token cap (incomplete checkpoint)`（L345，fail-closed）。
   另：`llm-deepseek` 的完成预留默认 **256,000**（`DEFAULT_MAX_TOKENS = 256e3`，L1155），
   正是"830,224 messages + 256,000 completion"里那个 256K 的来源。

### 本版修复（v1.10.24）
跟踪 `compaction/start` / `compaction/end` 会话事件，折叠**登记时**（`scheduleFold`）与**提交前**
（`foldBody`，覆盖 `pre-step` 直折这条不经 `scheduleFold` 的路径）各让路一次：
- compaction 在飞 ⇒ 本轮不折（`reason: 'compacting'`），**下一轮再折，内容不丢**（折叠是基于 surface 的无损推导）；
- `compaction/end` 即使带 `error` 也解除让路（否则一次失败的 compaction 会把折叠**永久钉死**）；
- 按 sid 隔离，其它会话不受影响。
回归：`CONTEXTinjector/compaction-guard.test.mjs` **3/3**（含"失败结束也要解除"与"只影响该会话"）。

### 建议的 DSH 侧配置（用户侧，改 `settings.yaml` 后重启 dsh web）
```yaml
llm-deepseek:
  maxTokens: 32768        # 完成预留（默认 256000）：830224 + 32768 = 862992 < 1048576 ⇒ 大上下文会话才装得下
  models:
    - id: deepseek-v4-flash
      maxTokens: 32768    # 也可只对单个模型设（优先级高于插件级）
compaction-basic:
  maxTokens: 32768        # 总结输出上限（默认 8192）⇒ 大 region 的 checkpoint 才写得完
```
代价：① 单次回复上限压到 32K 输出 token；② compaction 那次调用输出更长一点（只影响它自己）。

三、实证：什么时候该开 single / double（**single 的优势随轮数放大**）
--------------------------------------------------------------------------------
配对比值（billed，基线=不挂插件；来自本机多轮实测）：

| 配对比值 | 6 回合 | 12 回合 |
|---|---|---|
| single / bare | 0.834 | **0.449** |
| off / bare | 1.111 | 0.671 |
| single / off | 0.751 | **0.669** |

⇒ **长会话默认用 `single`；`off`（纯无损折叠）在短会话是净亏（1.111）、长会话才转正**。
判据仍看 `last-fold`：`aCount/aFolded`、`fallbackReasons`、`keys`、`shrink`、`aux*`（辅助调用计量）。
注意 `ms` 会被机器休眠放大，不能当算力时间读。
