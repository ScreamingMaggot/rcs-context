RCS 0.1.20 改进与保留项
================================================================================
插件版本：CONTEXTinjector v1.10.25
打包基线：v1.10.24（compaction 让路）+ 本版新增的计量修复与经济性口径
本包含并：0.1.19 的全部改动（其说明随包分发）
回退点：rcs-0.1.19 → rcs-0.1.18 → … → rcs-0.1.8（未含多段转录的稳定点）

--------------------------------------------------------------------------------
一、本版为什么重要：一次"数据说折叠没有收益"的误判，根因是**我们的计量是瞎的**
--------------------------------------------------------------------------------
2026-09-14 的付费跑批（`实证数据-Fplus\RCS-0.1.19-task`）分析给出了与事实相反的结论：

    "转录被重复注入 ~29 次（2,020,741B / 70,269B = 28.8×），折叠加在 3% 的窗口上 ⇒ 折叠没有收益"

三处硬错（逐条可复算，见 `docs\DESIGN-prompt-cost-accounting.md`）：

1. **请求里只有一份转录。** 插件每次提交折叠后把 `session.deriveMessages()`（即将发送的真实消息
   结构）写进 `injector.jsonl` 的 `after`。11 个折叠臂、**63 次提交/臂**，每次请求都是**3 条消息**：
   用户 127B + 注入面 400B + 转录 ≈62KB。**没有任何一次出现两份。**
2. **2,020,741B 是"日志的历史"，不是"请求的体量"。** 每轮折两次（`turn-stopping` + `turn-end`）
   ⇒ 32 轮 = 63 次提交；单段转录每次提交都**重写整份转录文本**，追加式日志因此留下 63 份"当时全文"。
   把它们累加 ÷ 末态全文 = **27.3×–33.8×**（复算值与 28.8× 同源）—— 它度量的是**提交次数**。
3. **用量算术直接否掉"29 份"。** A01-off-1 实测 93 步、输入 token 合计 1,670,927（≈1.67M，17,967/步）。
   若请求里真有 2.02MB 转录（≈50 万 token），**单次请求**就已超过该跑次总量 ⇒ 与实测差 **28 倍**。

**被这次误判掩盖的真缺陷（本版修复）**：`messageBytes()` 的 tool-result 分支写的是
`tr:${b.name}:${b.content}`，而 `content` 在真机上是**块数组**
（`{"type":"tool-result","toolCallId":"…","content":[{"type":"text","text":"…"}]}`）
⇒ 模板串一律得到 `"[object Object]"`，**几十 KB 的工具结果只算 ~30B**。
工具正文恰是折叠要压掉的大头（夹具 159KB 工具正文 / 185KB 总量）⇒ 主指标
`shrink = transcriptBytes/shadowedBytes` 对收益**结构性失明**：长期停在 0.998
既不是"只省了 0.2%"，也不是"折叠有效"，而是**不含信息**。

--------------------------------------------------------------------------------
二、0.1.20 新增（v1.10.25）
--------------------------------------------------------------------------------
1. **计量修复**：`messageBytes` 计入嵌套工具正文（新增 `blockTextOf`：字符串 / 块数组 /
   嵌套 `content` / 对象；`name` 缺失时退回 `toolCallId`）。回归测试含**负向断言**：
   40KB 工具结果必须按 ≥40,000B 计，且不得再出现 `"[object Object]"`。
2. **四个可对外的经济性量**（写进 `last-fold`、`fold-index` 的 `bytes.live/raw/appended`、
   `injector.jsonl`）：
   - `liveBytes`：提交后**真实请求**里的消息字节合计（唯一直接对应账单的字节量）
   - `incrementalRawBytes`：本折真正转写的**新**原料字节（已排除自身旧转录节点）
   - `appendedBytes`：本折追加进转录的字节
   - `foldRatio = appendedBytes / incrementalRawBytes`：**本折对新原料的压缩比（<1 才是省）**
   `shrink` 保留（面板/历史消费方零改动），但明确标注**非收益指标**：单段模式下被替换集合含
   "上一版转录节点本身" ⇒ 结构上恒 ≈1。
3. **raw 存证只存原料**：单段模式下旧转录节点的事件 seq 落在增量区间内 ⇒ 它曾每次折叠都被当成
   "被遮蔽原文"再存一遍。实测 A01-off-1：raw 存证 2,350,121B 里 **1,908,405B 是我们自己的转录**
   （62 行 / 63 折），真原料仅 223,038B ⇒ 体积 ~10× 虚高，且任何"把 raw 当原文来统计"的分析会把
   转录重复计入 62 次（与 29× 误判同源）。转录是 raw 的派生物，已在写入处过滤。
4. **新工具 `tools/measure-prompt-surface.mjs`**（只读、零成本）：把"请求里到底有几份转录"变成
   可复算的数字，并给出不变量闸门：
   - I1 每次提交的请求里转录量级（≥4KB）plugin 节点**至多 1 个**
   - I2 请求总字节 ≤ 最大单节点 + 8KB（没有未计入的大块）
   - I3 末态请求里的转录字节 == `last-fold.full` 字节（面板/索引/请求同源）
   付费跑批 11 个折叠臂全部 **PASS**；负向对照（人为把转录复制一份）已固定进测试，
   确保闸门不是安慰剂。

三、实测收益（同一批付费数据的正确口径）
--------------------------------------------------------------------------------
**机制层面**（同一段对话：不折叠的原文 ÷ 末态请求；本跑次内生，无跨臂混淆）：
A01 3.49× / A02 6.21× / A03 1.34× / A04 8.68× / A05 4.60× / A06 6.06× / A07 4.31× /
A08 13.10× / B01 8.79× ⇒ **中位 6.06×，区间 1.34–13.10×**
（A03 偏低：该跑次工具输出少、以助手文本为主，off 档保留 `[A]` 原文，折叠此时近乎"搬运"）。

**账单层面**（bare 不装插件 vs off 折叠不浓缩，n=1/格）：每步输入 token 比 **0.94–4.47×（中位 1.37×）**，
总量比 0.65–6.01×（中位 1.43×）。**臂间步数不同（差 0–60%）= 模型行为差异**，不是机制差异 ⇒
总量不可单独引用；这组数字**不作统计结论**（n=1）。

**与 0.1.19 §四（转录无界增长）的关系**：转录占末态请求 **99.2%**（63,371B / 63,898B）⇒
"钱花在转录上"成立，但不是因为重复注入，而是因为**它是唯一的大块**；且旧转录永不重压、
随会话线性增长。剩下最高价值的工作仍是 §四 的"对旧转录再压缩"，它风险最高（静默丢内容），
必须单独设计 + A/B，**不在本版范围**。

--------------------------------------------------------------------------------
四、保留项（已知未解，如实列出）
--------------------------------------------------------------------------------
1. **长会话转录无界增长**（0.1.19 §四 原样保留）：本版只让它**可见**（liveBytes / foldRatio /
   rawOverLive），未改压缩策略。
2. **浓缩档对新原料的覆盖率仍低**：`off` 档下 `[T]` 行只留摘要（这是收益来源），但 `[A]` 原文
   全保留；`single/double` 受 `condenseMinBytes`(240) 与 `tooShort` 限制，机制层实测参与度仅 9–20%。
3. **每轮折两次**（`turn-stopping` + `turn-end`）：增量设计使然，但带来日志/落盘写放大
   （每轮多写一份 ~60KB 的 `last-fold` 与节点体）。改它属行为变更，须单独 A/B。
4. **K 通道 `keysErr`** 仍有一处未定位（离线夹具里 double 档出现 1 次空产出，已在 0.1.19 记录）。
5. **DSH 侧配置建议不变**：`llm-deepseek.maxTokens` 与 `compaction-basic.maxTokens` 建议 ≥32768，
   否则 DSH 自身的 compaction 会 fail-closed（0.1.19 §二 复盘）。
